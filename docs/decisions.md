# Принятые решения


| ID  | Решение                                                                                                                                                                                                                                                                                                                                                               |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D01 | Два независимых LLM-агента управляют одним общим бюджетом. Выполнение задач моделирует Python, решения о действиях принимает LLM.                                                                                                                                                                                                                                     |
| D02 | У агента есть собственные задания и естественно-языковые приоритеты. Цену и длительность вариантов он узнаёт через инструмент. Численная полезность скрыта и нужна только проверяющему.                                                                                                                                                                               |
| D03 | Сравниваем B0 (без защиты и сообщений), B1 (сообщения), B2 (атомарное резервирование), B3 (оба механизма).                                                                                                                                                                                                                                                            |
| D04 | В B0/B1 сервер проверяет бюджет при принятии заявки, но списывает позднее, не резервируя деньги. В B2/B3 проверка и резервирование - одно действие; окончательное списание происходит позднее.                                                                                                                                                                        |
| D05 | Все агенты предлагают действия на одном логическом шаге до их исполнения. Очерёдность событий определяет симулятор, а не скорость ответа LLM.                                                                                                                                                                                                                         |
| D06 | Принятая заявка занимает работу целиком: другой вариант этой же работы уже нельзя запускать. Отказ из-за бюджета позволяет выбрать другую работу или вариант. Отмен, возвратов и изменения стоимости в первой версии нет.                                                                                                                                             |
| D07 | Два слоя проверки: сначала заранее заданные действия без LLM, затем настоящие LLM-агенты. Нарушения проверяем по журналу операций, не по словам агентов.                                                                                                                                                                                                              |
| D08 | Для пилота берём `Qwen3-4B-Instruct-2507` в Q4_K_M через Ollama на Apple Silicon, если хватает памяти и работает вызов инструментов. При технической несовместимости используем API только для пилота; модели не смешиваем в основном сравнении.                                                                                                                      |
| D09 | В парных запусках балансируем порядок A/B и перестановку пользовательских ролей; они одинаковы между сравниваемыми методами.                                                                                                                                                                                                                                          |
| D10 | Старые пилоты `13/30` храним как историю. Для новых сравнений единое окно `t=0..39`, подача с `t=40`, горизонт 80. Для проверки задержек сообщений используем 1, 4, 8 при раундах в `t=6,13,20`.                                                                                                                                                                      |
| D11 | H1 с LLM проверяем отдельной сеткой задержек и `start_gap`; S4 проверяем на разных новых сценариях и задержках, не считая повторы новыми задачами.                                                                                                                                                                                                                    |
| D12 | `U_safe=0` при нарушении бюджета, иначе `U`. Статистическая единица - профиль задачи; четыре повтора дают среднее на профиле. Интервалы по тестовому набору - с пересэмплированием целых профилей внутри семейств.                                                                                                                                                    |
| D13 | `wait_until`, `logical_time` и `submission_not_open` сохраняются; старый лимит 16 относится к прежним пилотам, лимит для нового набора - 24 решения на агента.                                                                                                                                                                                                        |
| D14 | Для повторов используем отдельные `environment_seed` и `llm_seed` (если поддерживается); пилотная `temperature=0.3`, итоговую фиксируем перед E2.                                                                                                                                                                                                                     |
| D15 | Нынешняя свободная коммуникация - вариант `F` и диагностический baseline. Улучшения не подменяют его: отдельно тестируем `R1`, `R3`, `R3P` по [DPBench](https://arxiv.org/abs/2602.13255).                                                                                                                                                                            |
| D16 | Работа, завершившаяся в `t=horizon`, засчитывается. Все сообщения - до открытия подачи; в назначенных раундах - только в `t=6,13,20`.                                                                                                                                                                                                                                 |
| D17 | Пилотная конфигурация: Ollama 0.40.17, `qwen3:4b-instruct-2507-q4_K_M`, ID `0edcdef34593`. Перед E2 подтверждаем её или заменяем, не смешивая модели в одном сравнении.                                                                                                                                                                                               |
| D18 | Вместо новых номеров B4/B5 применяем обозначение `U/` или `A/` (способ расходования) и `N`, `F`, `R1`, `R3`, `R3P` (протокол общения). Старые B0-B3 сохраняются как пары `U/N`, `U/F`, `A/N`, `A/F`.                                                                                                                                                                  |
| D19 | Собственный метод `A/VBC = A/R3P+S+V+G`: `S` - раскрытые структурированные предложения, `V` - проверка суммарной стоимости, `G` - подтверждение версии и контроль запуска. Отдельно проверяем `S` и полную схему `V × G`; среда не видит скрытую полезность и не выбирает уступающего агента. Основание - [*Talk is Cheap*](https://arxiv.org/abs/2605.01750), §§5-6. |
| D20 | Если оба не подтвердили одну версию плана, метод VBC переходит к обычной атомарной подаче и фиксирует `agreement_failed`, не выдавая fallback за состоявшуюся договорённость.                                                                                                                                                                                         |
| D21 | Для нового исследования создаём `dev` (10 профилей) и отдельный `test` (28 профилей: 4 S0, по 6 S1-S4). Старые 20 JSON используются как прежний пилот и контроль, а не как новый слепой тест. В `test` - четыре парных повтора по порядку и ролям.                                                                                                                    |
| D22 | Сначала отдельно меняем число раундов (`R1`/`R3`), затем инструкцию (`R3`/`R3P`), затем компоненты VBC. В `F`/`R1` одновременно меняется организация связи, поэтому это сравнение не называем чистой абляцией числа сообщений.                                                                                                                                        |
| D23 | В новых сценариях допускаем 1-3 работы на пользователя, альтернативы и зависимости `requires` между работами одного пользователя. Чужие работы и `value` не раскрываем автоматически.                                                                                                                                                                                 |
| D24 | Главная оценка метода - безопасная полезность относительно `U*`, при обязательной отчётности о превышениях, согласовании, соответствии действий плану, простоях и стоимости переговоров. Основной `test` не используем для настройки промптов.                                                                                                                        |

## Что фиксируем после технического пилота

- Точная версия модели/квантизации, устройство, доступная память, сервер и параметры генерации.
- Действительно ли модель корректно вызывает инструменты; если нет - согласованная замена.
- Реальная стоимость новых раундов и VBC, окончательная матрица сравнений и выбранные тестовые профили до запуска основного `test`.

Новые решения добавляем только когда реально изменили проект, а не после каждого обсуждения.
