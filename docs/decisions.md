# Принятые решения

| ID  | Решение                                                                                                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D01 | Два независимых агента представляют разных пользователей. LLM принимает решения, Python моделирует выполнение и расходы.                                                                                                                                     |
| D02 | Приоритеты - в пользовательском запросе; каталог цен, вариантов, длительностей и зависимостей - только `list_jobs()`. Статусы собственных работ могут отображаться автоматически. Общий лимит и остаток - `get_balance()`; поля названы `shared_budget`, `shared_available`, `shared_with`, чтобы ответ не читался как личный баланс. `value` доступна только оценщику. |
| D03 | Единые обозначения: `U`/`A` для списания; `N`, `F`, `R1`, `R3`, `R3P` для связи; VBC и его абляции - по таблице `system_spec.md`.                                                                                                                            |
| D04 | U проверяет бюджет при приёме, списывает позднее без резерва. A проверяет и резервирует атомарно, списывает после той же задержки.                                                                                                                           |
| D05 | Оба решения шага собираются до исполнения. Порядок задаёт симулятор, не скорость генерации LLM.                                                                                                                                                              |
| D06 | Не более одного принятого варианта работы; повтор одного request_id не списывает средства повторно. Отмена и возврат не предусмотрены.                                                                                                                       |
| D07 | E0 без LLM проверяет механизм, E1 на dev - все методы, E2-E4 на test - исследование. Аудит расходов независим от ответов агентов.                                                                                                                            |
| D08 | Две модели через API Mistral: `mistral-small-2603` и `deepseek-v4-1-flash-1017`; reasoning выключен, `max_tokens=2048`. Все серии на обеих, результаты отдельно. Полные параметры в `experiments.md`, §1; фиксируем манифест до test.                                                                                                                        |
| D09 | Четыре парных повтора: оба порядка и обе перестановки ролей; LLM-seed 0-3, seed среды из профиля.                                                                                                                                                            |
| D10 | Подготовка t=0..39, подача с t=40, горизонт 80; лимит 12+12 решений на агента. Индивидуальное открытие учитывает start_gap.                                                                                                                                  |
| D11 | H1 проверяем сеткой задержек списания и смещений; H2 - организацией общения и задержкой доставки; H3 - U/A; H4 - VBC против атомарных baseline и абляции.                                                                                                    |
| D12 | U_safe=0 при нарушении, иначе U; главный показатель качества - среднее U_safe/U* по профилям. Статистическая единица - профиль, не отдельный повтор.                                                                                                         |
| D13 | До индивидуального открытия подачи finish и submit_job отклоняются. Пробуждение по §5 `system_spec.md`; каждый агент имеет гарантированную возможность использовать назначенные слоты и исполнение в пределах лимитов.                                       |
| D14 | Температура 0.3; история не обрезается; параметры модели, промпты и схемы инструментов фиксируются до test.                                                                                                                                                  |
| D15 | R1 и R3 имеют одинаковую инструкцию и один/три communication-only раунда с send_message или skip_round; между раундами автоматическое ожидание; R3P добавляет только инструкцию о совместном бюджете. F/R1 - сравнение организации связи, не чистая абляция.                                                                                          |
| D16 | Завершение в horizon включено; сообщения отправляются до t=40, доставляются по заданной задержке.                                                                                                                                                            |
| D17 | VBC - самостоятельный протокол: предложения t=6, общий план t=7, раунд t=13 (второй при r=2 в t=20), пересмотр t=33, итоговый план t=35, подтверждение t=37.                                                                                                 |
| D18 | S раскрывает только добровольно переданные варианты; V возвращает проверенные числовые факты без выбора за агентов. Формат плана - компактный структурированный текст; остальные инструменты и сообщения не меняют формат.                                   |
| D19 | G ограничивает принятые заявки подтверждённой версией. Без соглашения - обычное атомарное исполнение. Подтверждение сверх бюджета разрешено, `agreed_over_budget` учитывается отдельно от допустимых соглашений.                                             |
| D20 | `data/scenarios/`: 10 dev, 28 test; seed генератора 20261123; фиксированный манифест и LF для JSON.                                                                                                                                                          |
| D21 | E1: 640 эпизодов; E2: 1232; E3: 240 дополнительных; E4: 144 + 96 дополнительных. Совпадающие условия из E2 используем повторно без нового запуска.                                                                                                           |
| D22 | 1-3 работы на пользователя, альтернативы, зависимости requires внутри одного пользователя.                                                                                                                                                                   |
| D23 | Технические сбои и ошибки агента различаем. Не исключаем неудачные решения; повтор технического сбоя - тот же ключ и конфигурация.                                                                                                                           |
| D24 | TLA⁺ проверяет конечные модели U, A и G; соответствие Python проверяется по трассам и тестам.                                                                                                                                                                |

Слово "обязательно" в запросе означает высокий приоритет; при недостатке бюджета агент может сам отказаться от работы, это учитывается по фактическому завершению главной работы. Среда не решает, кто уступает: отказ заявки означает только занятый общий бюджет (уточнено 2026-11-24 по согласованию с Всеволодом).

Ответы `submit_job` одинаково во всех вариантах: номер заявки нумеруется отдельно для каждого агента (общий счётчик выдавал активность партнёра, в том числе в N); отказ по бюджету сообщает `shared_available`, отказ по зависимости - незавершённых своих предшественников. Без этого агенты повторяли ту же заявку до исчерпания ходов, не зная причины отказа.

Экспериментальный дизайн, метрики и правила методов меняются только по согласованному решению команды. Полные определения - в `protocol.md`, `system_spec.md` и `experiments.md`.
