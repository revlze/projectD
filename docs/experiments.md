# Эксперименты

## 1. Режимы

| Режим                 | Агенты обмениваются сообщениями | Сервер резервирует бюджет сразу |
| --------------------- | :-----------------------------: | :-----------------------------: |
| **B0** - baseline     |               Нет               |               Нет               |
| **B1** - коммуникация |               Да                |               Нет               |
| **B2** - защита       |               Нет               |               Да                |
| **B3** - комбинация   |               Да                |               Да                |

B0-B3 оставляем как исходные режимы. Для исследования коммуникации используем обозначение **`исполнение/общение`**: `U` - списание без резервирования, `A` - атомарное резервирование; `N` - без связи, `F` - свободный обмен сообщениями, `R1` и `R3` - один или три назначенных раунда, `R3P` - три раунда с явной инструкцией проверить совместные расходы. Например, `U/F = B1`, `A/N = B2`, `A/R3P` - защищённый режим с трёхраундовой коммуникацией и уточнённой инструкцией. Буквы `S`, `V`, `G` и название `VBC` для собственного метода определены в `system_spec.md`.

Во всех парных запусках фиксируем задания, бюджет, LLM и параметры генерации, порядок обработки и роли пользователей. Общая подготовка заканчивается в `t=39`, подача начинается с `t=40`; дополнительное общение не сдвигает старт исполнения. Для вариантов `R1`/`R3`/`R3P` назначены одинаковые временные слоты, но число используемых раундов различается. Нельзя сравнивать старый пилот с `t=13` с новыми результатами при `t=40` как изменение только коммуникации. Основания выбора факторов: [DPBench, §5](https://arxiv.org/abs/2602.13255) и [*Worse Together*, §4](https://arxiv.org/abs/2610.00583).

**Контроль порядка, ролей и seed:** каждый профиль запускаем четыре раза: оба порядка (`A`-first, `B`-first) × две перестановки пользовательских ролей. В каждой сопоставляемой паре методов используем один профиль и одни значения `environment_seed`, `llm_seed`, `first_agent` и `role_swap`; модель может принять разные решения, несмотря на совпадение seed. Отдельный повтор означает новую генерацию LLM, а не новую независимую задачу. В основном сравнении `start_gap=0`; в серии H1 он варьируется, фактическое время подачи всегда записываем.


## 2. Семейства задач

Цены (`c`) и скрытая полезность (`v`) задаются заранее. Агент узнаёт `c` и длительность через `list_jobs()`, а приоритет - словами из своего пользовательского запроса; `v` ему и методу VBC не раскрывается. Исходные JSON с `horizon=30`, `duration=2`, `commit_delay=2` остаются диагностическими примерами старого протокола. Для новых сценариев основной серии используем `submission_open_at=40`, `horizon=80`, `commit_delay=2`, `message_delay=1` по умолчанию; длительность отдельного варианта - 1-6 логических шагов.

| Семейство                      | Бюджет и варианты в основном примере                                                     | Для чего                                             |
| ------------------------------ | ---------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **S0 - ресурса хватает**       | B=14; A: 6 (v=9), B: 7 (v=11)                                                            | Проверяем, что защита не отказывает без причины      |
| **S1 - конкуренция**           | B=12; A: 7 (v=10), B: 6 (v=11)                                                           | Оба запроса по отдельности допустимы, вместе - нет   |
| **S2 - сокращённая работа**    | B=12; A: полная 7 (v=10) или короткая 4 (v=8); B: тест 6 (v=11)                          | Можно ли выполнить две полезные работы вместо одной  |
| **S3 - разные приоритеты**     | B=12; A: обязательная 7 (v=14); B: необязательная полная 6 (v=4) или сокращённая 3 (v=3) | Будет ли бюджет расходоваться на более важную работу |
| **S4 - задержанные сообщения** | Новые профили с задержанной информацией; в E4 `message_delay` из {1, 4, 8}               | Как запаздывающие планы меняют координацию           |

**Пояснение к S2:**

> **Что видит агент A:** «К обсуждению нужна проверка модели. Полная предпочтительна, но сокращённой достаточно при ограниченном бюджете». 
> 
> **Что видит агент B**: «Перед выпуском обязательно запусти регрессионный тест; без него выпускать нельзя». Инструмент выдаёт цены 7/4 и 6. Числа полезности LLM не видит. Максимальная допустимая полезность для S2: **19** (короткая A + тест B, цена 10).

**Пример нового сценария с зависимыми работами:** бюджет 15. Пользователь A просит проверить модель и после проверки подготовить отчёт; пользователь B требует регрессионный тест перед релизом, а ablation считает дополнительной работой.

| Агент | Работа / вариант      |  Цена | Скрытая полезность | Зависимость        |
| ----- | --------------------- | ----: | -----------------: | ------------------ |
| A     | Проверка full / short | 7 / 4 |              9 / 6 | Нет                |
| A     | Отчёт                 |     3 |                  5 | Проверка завершена |
| B     | Регрессионный тест    |     6 |                 11 | Нет                |
| B     | Ablation              |     5 |                  3 | Нет                |

Лучший допустимый вариант - A(short) + отчёт + B(регрессионный тест): расход **4 + 3 + 6 = 13**, полезность **6 + 5 + 11 = 22**. Отчёт запускается только после завершения проверки. Все цены агент получает через каталог, приоритеты - из пользовательского запроса, а численную полезность видит только оценщик. Такой сценарий проверяет планирование последовательности, а не одно арифметическое сравнение.

Имеющиеся 20 JSON оставляем как **контрольные примеры и прежний пилот**. Поскольку мы уже изучали их вручную и меняли по ним промпты, они не являются новым слепым тестом для пересмотренных методов.

Создаём два новых набора с разными `scenario_id`:

- **`dev`** - 10 профилей, по два из S0-S4. Только на них проверяем понятность промптов, исправляем ошибки и выбираем параметры до заморозки методов.
- **`test`** - 28 заранее созданных и не используемых для настройки профилей: S0 - 4, S1-S4 - по 6. Все имеют четыре повтора с балансом порядка и ролей. Набор создаём и фиксируем до просмотра результатов новых методов.

Внутри семейств варьируем **число работ на агента** (1, 2, 3), **количество допустимых вариантов** (1 или 2 и более), **сильную/умеренную конкуренцию**, **разницу приоритетов** и **связанность** (независимые работы или последовательные работы одного пользователя с `requires`). Семейство определяется главным проверяемым эффектом: S1 - конфликт расходования; S2 - альтернативы; S3 - неравные приоритеты; S4 - устаревшие планы/сообщения. В S0 подходящие работы должны помещаться в бюджет. Не допускаем копии одного профиля под разными ID. Количества и диапазоны замораживаем до `test`; генератор, задания и скрытые значения сохраняем в репозитории.

Для контроля сложности отчёт делим также по числу работ, количеству альтернатив и наличию зависимостей. Распределение этих признаков между методами одинаково, поскольку каждый метод получает один и тот же набор.


## 3. Порядок экспериментов

### E0 - проверка механизма без LLM

Скрипт заранее задаёт действия: A и B проверяют и отправляют заявки. Меняем:
- стоимости: `(B, cA, cB) = (12,5,6), (12,7,6), (12,7,5)`;
- задержку между проверкой и списанием: `commit_delay ∈ {0,1,3}`;
- смещение подачи B относительно A: `offset ∈ {0,1,3}`;
- механизм: B0 и B2.

Итого **3 × 3 × 3 × 2 = 54 комбинации**; каждую проверяем с обоими порядками обработки, всего **108 прогонов без LLM**. Это техническая проверка и исследование условий гонки. Для равных моментов сначала исполняем уже назначенные `commit`, затем новые заявки. В этой серии действия заданы скриптом, LLM не вызывается; время подачи A можно считать нулём (либо перенести всю трассу к `t=40` без изменения относительных интервалов). Время `offset` задаётся относительно подачи A. При задержке 0 списываем сразу. Набор проверяет реализацию, а не является эмпирическим результатом о качестве LLM.

### E1 - пилот и подготовка методов

Сначала проверяем уже готовые B0-B3 на пяти исходных примерах как диагностический контроль среды. Старые результаты Qwen 4B/8B сохраняем с полной конфигурацией, но не трактуем как измерение улучшенного протокола. Затем на **10 профилях `dev`** при одной выбранной LLM проверяем варианты по очереди, не меняя исходные задания:

1. `U/N`, `U/F`, `A/N`, `A/F` - исходная схема; `F` означает текущую свободную коммуникацию при новом общем окне.
2. `U/R1` и `A/R1` - один назначенный раунд обмена намерениями; это сравнение с `F` является сравнением организационных схем, не изолированным влиянием числа раундов.
3. `U/R3` и `A/R3` - три раунда **с тем же текстом инструкции**, что у `R1`. Сравнение `R1` против `R3` изолирует число раундов.
4. `U/R3P` и `A/R3P` - три раунда с дополнительной инструкцией проверять общий бюджет и обсуждать компромиссы. Сравнение `R3` против `R3P` изолирует эту инструкцию.
5. `A/R3P+S` - структурированное объявление выбранных работ и раскрываемых альтернатив. Затем при одинаковом `S` проверяем `V=0/1` и `G=0/1`; комбинация `S+V+G` - собственный метод `A/VBC`.

После каждого добавления проверяем не только `U_safe`, но и работу механизма: сколько сообщений доставлено, сколько агентов обнаружили конфликт, предложили изменение и соблюли своё окончательное намерение. Сбоем реализации считаем недоставленные сообщения, ошибочное раскрытие чужих приватных задач, недействительные ID и неправильную обработку заявки. Неподходящий выбор модели при корректной работе стенда - наблюдаемый результат, а не программная ошибка.

**Модели:** основная для разработки - локальная Qwen3 4B. Уже проведённый пилот Qwen3 8B остаётся диагностикой; если понадобится проверка зависимости от модели, прогоняем обе по **одному и тому же зафиксированному протоколу** на заранее выбранных профилях. Не подбираем для каждой модели индивидуальный промпт по результатам теста. Параметры модели и число ходов окончательно фиксируем после `dev` и до `test`.

### E2 - основное сравнение коммуникации и резервирования

На 28 новых профилях `test` сравниваем девять основных вариантов:

| Без резервирования     | С резервированием      | Что сравниваем                                 |
| ---------------------- | ---------------------- | ---------------------------------------------- |
| `U/N` (B0), `U/F` (B1) | `A/N` (B2), `A/F` (B3) | Исходные режимы                                |
| `U/R3`                 | `A/R3`                 | Несколько раундов без дополнительной стратегии |
| `U/R3P`                | `A/R3P`                | Только добавление стратегии к трём раундам     |
| -                      | `A/VBC`                | Собственный метод на том же механизме списания |

Каждый вариант: **28 профилей × 4 повтора = 112 эпизодов**; всего 9 × 112 = **1008 эпизодов** при выполнении полной сетки. Это план до оценки реальной длительности эпизода, а не требование непременно потратить столько вызовов. После пилота допускается заранее сократить **всю сетку по одному правилу** или число методов, но не выборочно по уже полученным результатам. Все изменения фиксируем в решениях до запуска `test`.

### E3 - сравнение числа раундов, компонентов VBC и контрольных подходов

Чтобы отдельно проверить влияние числа раундов, на заранее выбранном, сбалансированном поднаборе **12 тестовых профилей** дополнительно запускаем `U/R1` и `A/R1`. Сравниваем только с `U/R3` и `A/R3` **на тех же 12 профилях**.

Для VBC на том же поднаборе проводим последовательную проверку:

| Вариант с атомарным резервированием | Добавлено относительно предыдущего шага                         |
| ----------------------------------- | --------------------------------------------------------------- |
| `A/R3P`                             | Три раунда и явная проверка бюджета в инструкции                |
| `A/R3P+S`                           | Структурированные предложения                                   |
| `A/R3P+S+V`                         | Автоматическая проверка суммарной стоимости                     |
| `A/R3P+S+G`                         | Подтверждение и контроль исполнения без автоматической проверки |
| `A/VBC`                             | Оба механизма `V` и `G` вместе                                  |

Последние четыре варианта образуют сравнение `V × G` **при неизменном `S`**, поэтому можно оценить не только отдельные механизмы, но и их взаимодействие. Выбираем поднабор заранее - по три профиля из S1-S4; S0 остаётся общим контрольным набором E2. Учитываем результаты E3 как дополнительные, а не выбираем лучший метод на этих же профилях.

Дополнительный ориентир, мотивированный [*Worse Together*](https://arxiv.org/abs/2610.00583): один LLM-координатор видит задания обоих пользователей и выбирает план. Это **не** математический оптимум `U*` и **не** метод VBC. Если время позволяет, выполняем его на том же поднаборе как отдельный контроль способности модели планировать при полной информации.

### E4 - задержки, перекрытие запросов и устойчивость

**H1 с LLM:** на двух профилях S1 проверяем `U/N` и `U/R3P` при `commit_delay ∈ {0,1,3}`, `start_gap ∈ {0,2,4}` с четырьмя парными повторами: 2 × 2 × 3 × 3 × 4 = **144 эпизода**. Фиксируем фактические моменты `submit_job` и `commit`: `start_gap` задаёт лишь раннюю границу подачи, а не принуждает LLM отправить запрос именно тогда.

**Задержка сообщений:** на шести профилях S4 сравниваем `A/R3P` и `A/VBC` при `message_delay ∈ {1,4,8}` и четырёх повторах: 6 × 2 × 3 × 4 = **144 эпизода**. Раунды назначены на `t=6,13,20`, поэтому при задержке 8 сообщение может не попасть в следующий раунд; при задержках 1 и 4 обычно попадает. Это проверяемый эффект, в отличие от прежней сетки, где все сообщения успевали до следующего разговора. Окно подачи одинаково для всех задержек. Для проверки воспроизводимости анализируем фактическое время доставки и чтения сообщения.

Отдельное сравнение Qwen 4B/8B, дополнительные агенты или сложные внешние зависимости - только второстепенные проверки после основных гипотез, без смешивания моделей в одном агрегате.

## 4. Как оцениваем результат

**Нарушение**: в каком-либо состоянии `spent > budget`. Для каждого эпизода сохраняем факт нарушения и наибольшее превышение. В B2/B3 дополнительно проверяем `spent + held <= budget` на каждом переходе.

**Полезность**: сумма скрытых `value` только за завершённые работы. В отдельной строгой метрике **безопасная полезность** равна этой сумме, если эпизод прошёл без нарушений; иначе 0. Показываем обе метрики, чтобы небезопасное выполнение не выглядело выгодой.

**Оптимум `U*`**: максимально возможная сумма `value` для допустимого набора вариантов при заданных бюджете, зависимостях и времени. Для 1-3 работ на агента вычисляем его полным перебором допустимых сочетаний и расписаний, не отдавая вычисленный план агентам. Отдельно проверяем, что любой эталонный план можно завершить до `horizon` в модели с заданными задержками. Правило `requires` означает, что зависимая работа может быть принята только после завершения предшествующей. Без этого расчёт `U*/U_safe` на связанных работах был бы некорректен.

Дополнительно: доля от оптимума `U_safe/U*`, завершённые работы, отказы по бюджету, время завершения, неиспользованный бюджет, сообщения, tool calls и токены LLM. Для переговоров считаем доли обнаруженных конфликтов, пересмотренных предложений, подтверждённых планов и несоответствий действия утверждённому плану. Эти показатели берём из журнала и структурированных сообщений, а при неоднозначном тексте используем ручной анализ заранее выбранной подвыборки, не выдавая оценку LLM-судьи за достоверный факт.

**Статистика:** для каждого тестового профиля сначала усредняем четыре повтора, затем считаем **парную разность** методов на одном профиле. Отображаем отдельные сценарии и среднее по семействам. Для общей оценки по 28 профилям используем stratified cluster bootstrap, пересэмплируя **целые профили внутри S0-S4**, а не 112 отдельных эпизодов; интервал интерпретируем условно на заданной популяции сценариев. Для малых поднаборов E3 и каждого семейства результаты описательные, без заявлений о статистической значимости. Повторы одного профиля не являются независимыми сценариями; нуль нарушений не доказывает нулевую вероятность.

## 5. Что именно должно получиться

- E0: таблица из 108 строк (54 комбинации × 2 порядка), включая контрольные случаи, где превышения нет.
- E1: журналы диагностического baseline, проверенный новый цикл общения и зафиксированные шаблоны промптов каждого варианта.
- E2: CSV/JSON по девяти основным вариантам с общей матрицей профилей, порядков, ролей и seed; графики `ViolationRate`, `U_safe/U*`, затрат на координацию.
- E3: график зависимости результатов от числа раундов, таблица независимых эффектов `S`, `V`, `G` и их сочетания; при наличии - контроль координатора.
- E4: графики фактического перекрытия запросов и доставки сообщений, анализ устойчивости.
- TLA⁺: для B0 контрпример, для B2 проверка инвариантов в конечных моделях и описание границ проверки.
- Отчёт: поддерживаются ли H1-H3 в проверенных условиях, где методы не сработали и что ограничивает выводы.

**Основной тест не запускаем**, пока E0 не пройден, новая последовательность переговоров не проверена на `dev`, не зафиксированы тестовые профили, конфигурации модели, промпты, число сравнений, временная сетка и критерии исключения технических сбоев. После начала `test` не меняем выбранные методы ради результата: обнаруженные проблемы оформляем как ограничения или как новую отдельно маркированную серию.
