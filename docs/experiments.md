# Эксперименты

## 1. Что сравниваем

| Режим | Агенты обмениваются сообщениями | Сервер резервирует бюджет сразу |
|---|:---:|:---:|
| **B0** - baseline | Нет | Нет |
| **B1** - коммуникация | Да | Нет |
| **B2** - защита | Нет | Да |
| **B3** - комбинация | Да | Да |

Во всех режимах два LLM-агента получают одинаковые для данного сценария пользовательские задания. Каталог стоимости, начальный бюджет, порядок обработки событий и модель LLM одинаковые. В B1/B3 разрешены `send_message` и `read_messages` и добавлена краткая инструкция о возможности координации. 

## 2. Пять семейств сценариев

Цены (`c`) и скрытая полезность (`v`) задаются заранее. Агенты видят `c`, но не `v`. `horizon = 20`, `duration = 2`, `commit_delay = 2`, `message_delay = 1`, если для отдельной проверки не сказано иное.

| Семейство | Бюджет и варианты в основном примере | Для чего |
|---|---|---|
| **S0 - ресурса хватает** | B=14; A: 6 (v=9), B: 7 (v=11) | Проверяем, что защита не отказывает без причины |
| **S1 - конкуренция** | B=12; A: 7 (v=10), B: 6 (v=11) | Оба запроса по отдельности допустимы, вместе - нет |
| **S2 - сокращённая работа** | B=12; A: полная 7 (v=10) или короткая 4 (v=8); B: тест 6 (v=11) | Можно ли выполнить две полезные работы вместо одной |
| **S3 - разные приоритеты** | B=12; A: обязательная 7 (v=14); B: необязательная полная 6 (v=4) или сокращённая 3 (v=3) | Будет ли бюджет расходоваться на более важную работу |
| **S4 - задержанные сообщения** | Как S2, но `message_delay` ∈ {0, 1, 3} | Как задержки коммуникации меняют координацию |

**Пояснение к S2:**

> **Что видит агент A:** «К обсуждению нужна проверка модели. Полная предпочтительна, но сокращённой достаточно, если нужно оставить ресурс на обязательные тесты». 
> 
> **Что видит агент B**: «Перед выпуском обязательно запусти регрессионный тест; без него выпускать нельзя». Инструмент выдаёт цены 7/4 и 6. Числа полезности LLM не видит. Максимальная допустимая полезность для S2: **19** (короткая A + тест B, цена 10).

`data/examples/` содержит **пять пилотных сценариев** (`s0_01`-`s3_01`, `s4_pilot`), **12 заранее подготовленных тестовых** (`s0_02`-`s3_04`) и три отдельные проверки задержки (`s4_01`-`s4_03`). Тестовые файлы нельзя использовать для настройки промптов.

## 3. Порядок экспериментов

### E0 - проверка механизма без LLM

Скрипт заранее задаёт действия: A и B проверяют и отправляют заявки. Меняем:
- стоимости: `(B, cA, cB) = (12,5,6), (12,7,6), (12,7,5)`;
- задержку между проверкой и списанием: `commit_delay ∈ {0,1,3}`;
- смещение подачи B относительно A: `offset ∈ {0,1,3}`;
- механизм: B0 и B2.

Итого **3 × 3 × 3 × 2 = 54 полностью заданных прогона без LLM**. Это техническая проверка и исследование условий гонки. Для равных моментов сначала исполняем уже назначенные `commit`, а затем новые заявки. Для повторов фиксируем соответствующий `seed` окружения во всех четырёх режимах (например, базовый seed сценария + номер повтора); случайные тексты LLM этот seed не гарантирует. При задержке 0 списываем сразу.

### E1 - пилот с LLM

Берём пять пилотных файлов (`s0_01`, `s1_01`, `s2_01`, `s3_01`, `s4_pilot`) и запускаем все B0–B3: 20 эпизодов. Цель - проверить вызовы инструментов, доступность сообщений, понятность пользовательских задач, время и стоимость одного эпизода. Результаты пилота не добавляем в основной тест. Если ноутбук не справляется, сокращаем пилот до S1/S2 и фиксируем причину; решение принимаем до основного теста.

### E2 - основное сравнение

Используем по три заранее подготовленных тестовых сценария S0-S3 (`*_02`, `*_03`, `*_04`; всего 12), для каждого - B0–B3. Предварительный протокол предусматривает 10 повторов: `12 × 4 × 10 = 480 эпизодов`. Сценарии и промпты фиксируются до запуска. Это основной эксперимент после пилота, не задача на один вечер. Если ноутбук не справится, число повторов можно пересмотреть только до просмотра основного теста, с явной правкой `protocol.md`; нельзя менять его выборочно по полученным результатам.

Для H1 отдельно сравниваем в E0 зависимость нарушений от перекрытия. Для H2 в E2 анализируем пары B0/B1 и B2/B3; для H3 - B2/B3, безопасную полезность и долю от оптимума. Оценка влияния задержек сообщений - отдельный E3.

### E3 - влияние задержки сообщений

Берём отдельный набор `s4_01`-`s4_03` (одинаковые задания S2-типа, `message_delay ∈ {0,1,3}`) в B1/B3, по десять повторов: 60 эпизодов. B0/B2 используем как ориентиры из E2, но не выдаём повторы одного и того же сценария за новые независимые наблюдения. Если сообщения не используются моделью, это тоже результат; отдельно фиксируем частоту отправки и чтения сообщений.

## 4. Как оцениваем результат

**Нарушение**: в каком-либо состоянии `spent > budget`. Для каждого эпизода сохраняем факт нарушения и наибольшее превышение. В B2/B3 дополнительно проверяем `spent + held <= budget` на каждом переходе.

**Полезность**: сумма скрытых `value` только за завершённые работы. В отдельной строгой метрике **безопасная полезность** равна этой сумме, если эпизод прошёл без нарушений; иначе 0. Показываем обе метрики, чтобы небезопасное выполнение не выглядело выгодой.

**Оптимум `U*`**: максимально возможная сумма `value` среди допустимых комбинаций вариантов при данном бюджете, с учётом ограничения «не больше одного варианта работы». Для небольших сценариев считаем полным перебором. В первой версии все задания можно успеть до горизонта при немедленной подаче; иначе оптимум должен учитывать и время.

Дополнительно: завершённые работы, отказы по бюджету, время завершения, количество сообщений, вызовов инструментов, токены LLM. В отчёте - число эпизодов, доли с доверительными интервалами Wilson и разброс полезности по сценариям. Нулевое число нарушений в выборке - не математическое доказательство безопасности.

## 5. Что именно должно получиться

- E0: таблица из 54 строк, включая контрольные случаи, где превышения нет.
- E1: полные журналы 20 пилотных эпизодов (или зафиксированного сокращённого пилота), проверенный агентный цикл.
- E2/E3: CSV/JSON по эпизодам и графики зависимости нарушений и полезности от режима/условий.
- TLA⁺: для B0 контрпример, для B2 проверка инвариантов в конечных моделях и описание границ проверки.
- Отчёт: поддерживаются ли H1–H3 в проверенных условиях, где методы не сработали и что ограничивает выводы.

**Основной тест не запускаем**, пока E0 не пройден, LLM корректно использует инструменты и зафиксированы конфигурации/промпты/финальное число повторов. Это защита от подгонки под результаты, а не бюрократия.
