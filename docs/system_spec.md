# Техническая спецификация среды

## 1. Данные эпизода

- `budget: int > 0` - общий невосполняемый лимит кредитов.
- `agents` - первоначально два идентификатора, каждому соответствует отдельный пользовательский запрос.
- `jobs` - 1-3 работы на агента; каждая работа принадлежит одному агенту и имеет уникальный `job_id`.
- `options` - допустимые варианты выполнения работы с `option_id`, `cost: int > 0`, `duration: int > 0`, скрытым `value: int >= 0`. Для одной работы можно принять не более одного варианта.
- `horizon: int > 0` - конец эпизода. Полезность начисляется за завершение работы до конца горизонта.
- `commit_delay: int >= 0`, `message_delay: int >= 0`, `seed` и лимит ходов агента - параметры сценария/запуска.

**Что известно агенту:** текст своего запроса (важность и допустимые компромиссы), собственные варианты с ценами и длительностями через каталог, текущий доступный баланс через инструмент. Не доступны чужие задания, скрытые оценки `value` и внутренний журнал. Чужие намерения появляются только в полученных сообщениях B1/B3.

Первые пять примеров находятся в `data/examples/s0_*.json` ... `s4_*.json`. Они нужны для разработки и пилота; данные основного теста создаются и фиксируются отдельно до запуска.

## 2. Состояние среды

- Работа: `not_started` → `pending` (запрос принят) → `running` (средства списаны) → `completed` (длительность истекла). Отказ не переводит её в `pending`; агент может попробовать другое действие.
- `spent` - сумма фактически списанных кредитов. 
- `held` - сумма кредитов, зарезервированных, но ещё не списанных. В B0/B1 `held = 0`.
- `available = budget - spent - held`. В небезопасном режиме остаток может стать отрицательным, это и есть наблюдаемое нарушение.
- Завершение работы не возвращает кредиты. Полезность начисляется только завершённой до `horizon` работе.
- Если уже при подаче заявки известно, что `t + commit_delay + duration > horizon`, среда возвращает `too_late`, не принимая и не списывая её. Это одинаковое правило во всех режимах.
- Если уже принят один вариант работы, второй отклоняется, даже если запрос пришёл до её завершения.

## 3. Инструменты

Агент - это LLM с историей сообщений и ограниченным набором действий. В каждом логическом ходе один активный агент может выбрать **одно** действие:

| Вызов | Правило |
| --- | --- |
| `list_jobs()` | Только свои задания, доступные варианты, цены и длительности. Без `value`. |
| `get_balance()` | Возвращает **снимок** `available` на момент выполнения вызова. Снимок предназначен для планирования, **не даёт права на списание**. |
| `submit_job(job_id, option_id, request_id)` | Проверяет владельца, существование варианта и отсутствие ранее принятого варианта той же работы. Затем запускает проверку бюджета согласно режиму, возвращает принятие/отказ. Саму стоимость агент указать не может. |
| `get_status()` | Статусы собственных работ и последнего запроса. |
| `send_message(agent_id, text)` / `read_messages()` | Только B1/B3. Сообщения доставляются с заданной логической задержкой. Не резервируют деньги и не являются транзакцией. |
| `finish()` | Агент прекращает подавать команды. Уже запущенные работы продолжаются до завершения или горизонта. |

`request_id` присваивается внутри Python-среды каждому вызову, LLM не должна генерировать его сама. Повторная доставка вызова с тем же ID не списывает средства снова. Агент не может напрямую устанавливать стоимость, полезность или бюджет.

Начальная инструкция одна по смыслу для всех режимов: выполнять наиболее важные работы, учитывать доступный бюджет, использовать инструменты, не выдумывать их результаты. В B1/B3 добавляется только возможность обмена сообщениями. Разным пользователям можно задавать разные приоритеты.


## 4. Главное различие B0/B1 и B2/B3

Когда агент вызывает `submit_job` в момент `t`, сам сервер проверяет бюджет и правильность заявки.

**B0/B1: без резервирования.** Проверяем `budget - spent >= cost`. Если хватает - отвечаем `accepted`, переводим работу в `pending`, планируем списание на `t + commit_delay`. Кредиты пока не занимаем. В момент списания повторной проверки **нет**. Поэтому два запроса, принятые до первого списания, могут вместе превысить бюджет.

**B2/B3: атомарное резервирование.** Проверяем `budget - spent - held >= cost` и, если хватает, сразу увеличиваем `held`. Это одна неделимая операция. В момент `t + commit_delay` уменьшаем `held` и увеличиваем `spent` на ту же сумму. Если не хватает - `insufficient_budget`, состояние бюджета неизменно.

`commit_delay = 0` означает немедленное списание прямо при обработке заявки. При большем значении списание - событие в будущем. В обоих режимах фактический запуск работы происходит при списании; событие `completed` назначается на `commit_time + duration`.

Для любого режима запрещено дважды принять разные варианты одной работы, принять чужую работу или изменить цену, переданную в каталоге.

**Инварианты:**

1. Во всех режимах `spent >= 0`, `held >= 0`, `spent` равно сумме коммитов, одна работа не может иметь два принятых варианта.
2. В B2/B3 всегда `spent + held <= budget`.
3. При неатомарном режиме нарушение возможно, но не обязательно для каждого сценария. Оно возникает только если соответствующие проверки перекрываются.

## 5. Как совмещаем действия двух LLM

Используем дискретное время, которое контролирует Python. Реальная скорость генерации LLM не определяет победителя гонки.

На шаге `t`:

1. Выполняем все ранее назначенные события со временем `<= t`: списания, завершения, доставка сообщений. При равном времени используем порядок события и стабильный номер постановки в очередь.
2. Для каждого активного агента запрашиваем ровно одно следующее действие. Сначала собираем решения обоих, затем выполняем; агент B не видит результаты действий A из этого же шага.
3. Выполняем действия в заданном порядке (сначала A, затем B; при отдельных проверках можно менять порядок). Новые будущие события заносим в очередь. Если `commit_delay = 0`, списание выполняем непосредственно при обработке вызова.
4. Ответы инструментов попадают в историю соответствующего агента к следующему его ходу. Переходим к `t + 1`.

Для пилота ограничиваем агента 10 ходами, максимум одним tool call за ход. Невалидный вызов фиксируем как ошибку агента, бюджет не меняем. Сетевые сбои LLM фиксируем отдельно, не называем отказом по бюджету. Сообщения в B1/B3 доставляются через `message_delay`; сами по себе они не резервируют кредиты. По окончании ходов продолжаем обрабатывать уже запланированные работы до `horizon`.

## 6. Что обязательно писать в журнал

Каждая фактическая операция: `scenario_id`, режим B0–B3, время симуляции, `agent_id`, `request_id`, тип события, работа/вариант, стоимость, `spent_before`, `spent_after`, `held_before`, `held_after`, результат/причина отказа. Отдельно сохраняем решения LLM, тексты сообщений, модель и параметры генерации. Секреты не записываем.

Проверяющий анализатор заново суммирует только события `commit`, не доверяя полю `spent` из симулятора, и отмечает моменты, когда расход превысил `budget`. Проверяет также двойное принятие работы, переходы состояний и соответствие резервов операциям.

## 7. Минимальные тесты, которые должны пройти до LLM

| Тест  | Сценарий                                                      | Результат                                                                  |
| ----- | ------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `T01` | B0, бюджет 12, A=7 и B=6; оба приняты до списания             | оба `accepted`, после двух `commit` `spent=13`                             |
| `T02` | B2, те же действия                                            | одна заявка принята, вторая `insufficient_budget`, максимум `spent+held=7` |
| `T03` | B0, бюджет 12, A=5 и B=6                                      | оба завершены, `spent=11`, нарушений нет                                   |
| `T04` | B0, бюджет 12, A=7 и B=6, но B приходит после списания A      | B получает отказ, превышения нет                                           |
| `T05` | B2, работа A: full=7 или short=4; B=6                         | допускается A(short)+B, два варианта A одновременно запрещены              |
| `T06` | Повтор одного `request_id`                                    | только одна принятая операция, расход не удваивается                       |
| `T07` | Один сценарий и одинаковые seed/скриптовые действия           | одинаковые журнал и результат при повторном запуске                        |
| `T08` | Некорректный `job_id` / чужая работа / слишком поздний запуск | отказ без изменения бюджета                                                |

В тестах `T01–T08` действия агентов заранее заданы, LLM ещё не участвует. `T01` намеренно воспроизводит ошибку - это успешный тест, а не провал проекта. Первая реализация готова, когда все восемь проверок проходят.
