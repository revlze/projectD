# Техническая спецификация среды

## 1. Данные эпизода

- `budget: int > 0` - общий невосполняемый лимит кредитов.
- `agents` - первоначально два идентификатора, каждому соответствует отдельный пользовательский запрос.
- `jobs` - 1-3 работы на агента; каждая работа принадлежит одному агенту и имеет уникальный `job_id`.
- `options` - допустимые варианты выполнения работы с `option_id`, `cost: int > 0`, `duration: int > 0`, скрытым `value: int >= 0`. Для одной работы можно принять не более одного варианта.
- `horizon: int > 0` - конец эпизода. Полезность начисляется за завершение работы до конца горизонта.
- `commit_delay: int >= 0`, `message_delay: int >= 0`, `seed` и лимит ходов агента - параметры сценария/запуска.

**Что известно агенту:** текст своего запроса (важность и допустимые компромиссы), собственные варианты с ценами и длительностями через каталог, текущий доступный баланс через инструмент. Не доступны чужие задания, скрытые оценки `value` и внутренний журнал. Чужие намерения появляются только в полученных сообщениях B1/B3.

Первые пять примеров находятся в `data/examples/s0_*.json` ... `s4_*.json`. Они нужны для разработки и пилота; данные основного теста создаются и фиксируются отдельно до запуска.

## 2. Состояние среды

- `spent` - сумма списаний по уже совершённым операциям `commit`.
- `held` - сумма активных резервирований в B2/B3; в B0/B1 всегда ноль.
- `available = budget - spent - held` - доступные кредиты (в B0/B1 может быть отрицательным после гонки).
- `job_status`: `not_started`, `pending`, `running`, `completed`; отдельное поле хранит последний отказ. Принятое задание не отменяется, кредит не возвращается.
- Очередь событий и журнал переходов. У каждого запроса есть отдельный `request_id`; повторный запрос с тем же ID не исполняется заново.

## 3. Инструменты

| Вызов | Правило |
| --- | --- |
| `list_jobs()` | Только свои задания, доступные варианты, цены и длительности. Без `value`. |
| `get_balance()` | Возвращает **снимок** `available` на момент выполнения вызова. Снимок предназначен для планирования, **не даёт права на списание**. |
| `submit_job(job_id, option_id, request_id)` | Проверяет владельца, существование варианта и отсутствие ранее принятого варианта той же работы. Затем запускает проверку бюджета согласно режиму, возвращает принятие/отказ. Саму стоимость агент указать не может. |
| `get_status()` | Статусы собственных работ и последнего запроса. |
| `send_message(agent_id, text)` / `read_messages()` | Только B1/B3. Сообщения доставляются с заданной логической задержкой. Не резервируют деньги и не являются транзакцией. |
| `finish()` | Агент прекращает подавать команды. Уже запущенные работы продолжаются до завершения или горизонта. |

Ошибочные ID, повторный вариант уже принятой работы и некорректные аргументы отклоняются без изменения бюджета. Отказ из-за нехватки бюджета не блокирует выбор другого варианта работы в последующем ходу. Неуспешный LLM-вызов фиксируется отдельно от осмысленного отказа агента.

## 4. Единственная разница B0/B1 против B2/B3

При `submit_job` среда выполняет проверку допуска в момент `t` и планирует списание (`commit`) на `t + commit_delay`.

- **B0/B1 - check-then-spend:** при проверке допуска смотрим текущий `budget - spent`; если хватает, помечаем работу `pending`, но **ничего не резервируем**. При `commit` списываем уже проверенную сумму **без новой проверки**. Если два запроса прошли проверку до первого списания, возможен `spent > budget`.
- **B2/B3 - atomic reserve:** при проверке допуска одним неделимым переходом проверяем `budget - spent - held >= cost` и увеличиваем `held` на `cost`. Иначе отклоняем запрос. При `commit` переносим сумму из `held` в `spent`: общий объём `spent + held` не меняется.

В обеих реализациях `commit` наступает после одинаковой задержки. После него работа становится `running`, а в момент `commit_time + duration` - `completed` (если не вышли за `horizon`). Это позволяет отделить эффект резервирования от разницы в длительности исполнения.

**Инварианты:**

1. Во всех режимах `spent >= 0`, `held >= 0`, `spent` равно сумме коммитов, одна работа не может иметь два принятых варианта.
2. В B2/B3 всегда `spent + held <= budget`.
3. При неатомарном режиме нарушение *возможно*, но не обязательно для каждого сценария. Оно возникает только если соответствующие проверки перекрываются.

## 5. Планировщик и агентный цикл

- Симулятор использует очередь `(logical_time, event_priority, insertion_order, event)`. Перед обработкой очередного хода доставляются все уже назначенные события с временем `<= t` (включая `commit` и сообщения). Новые вызовы инструментов внутри одного хода исполняются по фиксированному порядку агентов; в B0 их проверки могут пройти до будущих `commit`, в B2 первое резервирование уменьшает остаток для второго. Порядок равных событий фиксируется `event_priority` и порядком постановки в очередь. `seed` определяет внешние задержки и (если нужно) перестановку порядка при равенстве, а не тексты ответов LLM.
- Нельзя обслуживать каждого LLM-агента целиком до перехода к следующему: тогда конкурентность исчезнет. На пилоте используем синхронные «ходы»: на каждом ходе каждый активный агент может предложить не более одного действия. Все предложения хода собираются до изменения состояния инструментов, затем применяется детерминированный порядок обработки и доставляются ответы.
- Внутренние события (`commit`, завершение работ, доставка сообщений) обрабатываются по логическому времени. Нельзя использовать фактическую длительность сетевого LLM-запроса для определения победителя гонки.
- В исходном сравнении всем режимам задаются одинаковые: пользователи, каталог задач, стоимость/длительность, бюджет, horizon, число доступных ходов, базовые инструкции и расписание внешних событий. Для B1/B3 добавляются только сообщение как инструмент и краткое описание его применения.
- Устанавливаем предел в **12 ходов на агента** для пилота; горизонт и задержки конкретного сценария задаются отдельно. Если LLM предложила несколько вызовов за один ход, исполнение отклоняется как некорректный формат (для основного теста предпочтительнее `parallel_tool_calls=false` на стороне API).

## 6. Контрольный сценарий (S1)

`budget=12`, агент A: работа `qa` вариант `full` стоимостью 7; агент B: работа `regression` стоимостью 6. Оба подают `submit_job` до первого `commit`, `commit_delay=2`, `duration=1`.

| Событие | B0/B1: без резервирования | B2/B3: с резервированием |
| --- | --- | --- |
| Оба успевают прочитать баланс | 12 и 12 | 12 и 12 |
| Заявка A (7) | Принята, `held=0` | Принята, `held=7` |
| Заявка B (6) до `commit A` | Принята, `held=0` | Отказ: осталось 5 |
| После коммитов | `spent=13`, нарушение | `spent=7`, нарушения нет |

В сценарии S2 к этому набору добавляется альтернатива A «сокращённая проверка за 4» и скрытые полезности: полная A - 10, сокращённая A - 8, B - 11. Эталонная допустимая полезность - `8+11=19` при расходе `4+6=10`.

## 7. Первая граница реализации

**В первый PR:** типы заданий, проверка схемы входа, общий ресурс, два механизма B0/B2, дискретные события, журнал фактических операций, тесты S0/S1/S2 без LLM. Пока без отмен, возвратов, зависших заявок, реальных вычислений и сложных сообщений.

**Во второй PR:** модель LLM, инструменты, агентный цикл и коммуникация B1/B3; сценарии S3/S4, пилот и логирование токенов. Затем фиксируем параметры основного теста.
