# Техническая спецификация среды

## 1. Данные эпизода

- `budget: int > 0` - общий невосполняемый лимит кредитов.
- `agents` - два идентификатора, каждому соответствует отдельный пользовательский запрос.
- `jobs` - 1-3 работы на агента; каждая принадлежит одному агенту и имеет уникальный `job_id`. Опциональное поле `requires` перечисляет другие работы **этого же пользователя**, которые нужно завершить до запуска данной работы; зависимости образуют ориентированный ациклический граф.
- `options` - допустимые варианты выполнения работы с `option_id`, `cost: int > 0`, `duration: int > 0`, скрытым `value: int >= 0`. Для одной работы можно принять не более одного варианта.
- `horizon: int > 0` - конец эпизода. Полезность начисляется за завершение работы не позже `horizon` (момент `t = horizon` включён).
- `commit_delay: int >= 0`, `message_delay: int >= 0`, `environment_seed`, `llm_seed` (при поддержке сервера), лимит ходов и `start_gap` - параметры сценария/запуска. Реальный отклик LLM не меняет логическое время. Фиксируем `submission_open_at=40`, `horizon=80`, `agent_turn_limit=24` (12 решений на подготовку и 12 на исполнение).

**Что известно агенту:** текст собственного пользовательского запроса; ID и состояния своих работ в наблюдении; каталог вариантов, цены, длительности и зависимости только через `list_jobs()`; общий бюджет и текущий доступный остаток только через `get_balance()`. Ответы инструментов сохраняются в истории агента. Наблюдение не повторяет каталог, цены или длительности. Чужие работы и альтернативы раскрываются только другим агентом в сообщениях или структурированных предложениях. Скрытая `value` доступна лишь оценщику, но не LLM и не верификатору. Проверки чужих или несуществующих ID возвращают одинаковую общую ошибку без подтверждения их существования.

`data/scenarios/` содержит `dev` (10 профилей), `test` (28 профилей) и `manifest.json` с хешами, признаками сложности, `U*` и фиксированным поднабором E3. JSON и манифест хранятся в UTF-8 с LF. Состав набора и его контрольные суммы фиксируются до экспериментов.

## 2. Состояние среды

- Работа: `not_started` → `pending` (запрос принят) → `running` (средства списаны) → `completed` (длительность истекла). Отказ не переводит её в `pending`; агент может попробовать другое действие.
- `spent` - сумма фактически списанных кредитов. 
- `held` - сумма кредитов, зарезервированных, но ещё не списанных. В вариантах `U/*` `held = 0`.
- `available = budget - spent - held`. В небезопасном режиме остаток может стать отрицательным, это и есть наблюдаемое нарушение.
- Завершение работы не возвращает кредиты. Полезность начисляется только работе, завершённой не позже `horizon` включительно.
- Если уже при подаче заявки известно, что `t + commit_delay + duration > horizon`, среда возвращает `too_late`, не принимая и не списывая её. Это одинаковое правило во всех режимах.
- Если уже принят один вариант работы, второй отклоняется, даже если запрос пришёл до её завершения.
- Если у работы есть `requires`, заявка отклоняется с `prerequisite_not_completed`, пока все указанные предшественники не стали `completed`. Нельзя обходить это условие сменой варианта.

## 3. Инструменты

Агент - это LLM с историей сообщений и ограниченным набором действий. В каждом логическом ходе один активный агент может выбрать **одно** действие:

| Вызов                                              | Правило                                                                                                                                                                                                              |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list_jobs()`                                      | Только свои задания, доступные варианты, цены и длительности. Без `value`.                                                                                                                                           |
| `get_balance()`                                    | Возвращает общий для обоих агентов `shared_budget`, **снимок** общего остатка `shared_available` на момент вызова и `shared_with` - ID другого агента. Снимок предназначен для планирования, **не даёт права на списание**.                                                                       |
| `submit_job(job_id, option_id)`                    | Проверяет владельца, существование варианта и отсутствие ранее принятого варианта той же работы. Затем запускает проверку бюджета согласно режиму, возвращает принятие/отказ. Отказ `insufficient_budget` содержит снимок `shared_available`, отказ `prerequisite_not_completed` - список своих незавершённых предшественников `waiting_for`. Саму стоимость агент указать не может. |
| `get_status()`                                     | Статусы собственных работ и последнего запроса.                                                                                                                                                                      |
| `send_message(agent_id, text)` / `read_messages()` | В F отправка до t=40 и чтение через инструмент; в R1/R3/R3P отправка только в слоте, доставка показывается автоматически. Для S действуют свои фазы. Сообщения доставляются с заданной логической задержкой. Не резервируют деньги и не являются транзакцией.      |
| `wait_until(target_time)`                          | Приостановить агента до логического времени `target_time`; не вызывать LLM на пропускаемых шагах. Правила пробуждения заданы в разделе 5.                                                                            |
| `skip_round()`                                    | Только в назначенном раунде: явный пропуск без сообщения, расходует одно решение. |
| `finish()`                                         | После индивидуального открытия подачи прекращает принимать решения. До открытия - `finish_not_open`, без завершения агента.                                                                                          |

`request_id` присваивается внутри Python-среды каждому вызову `submit_job` с отдельной нумерацией для каждого агента (`A-r0`, `A-r1`, `B-r0`...), чтобы номер не выдавал число заявок партнёра; LLM не должна генерировать его сама. Повторная доставка вызова с тем же ID не списывает средства снова. Агент не может напрямую устанавливать стоимость, полезность или бюджет. В системной инструкции и ответах инструментов агент видит `logical_time` и `submission_open_at`; время изменяет только симулятор. `wait_until` принимает целое время позже текущего (не позже `horizon`): сам вызов расходует один ход LLM, последующее ожидание - нет. Вызов с неверным временем отклоняется; разрешённое ожидание не расходует дополнительные решения.

Начальная инструкция одна для всех вариантов; различаются только явно заданные дополнения из разделов 5 и 6. Полные системные инструкции, схема инструментов, шаблоны наблюдений и хеши фиксируются перед `test`. Изменения допускаются на `dev` только для исправления несоответствия спецификации или как отдельный исследуемый фактор; после исправления заново запускаем затронутые сравнения.

## 4. Механизм списания: U и A

Время открытия подачи задаётся для каждого агента отдельно: для `first_agent` - `submission_open_at = 40`, для другого - `40 + start_gap`. `first_agent` - первый агент в выбранном для повтора порядке обработки (`A`-first или `B`-first); перестановка пользовательских заданий (`role_swap`) этого порядка не меняет. `start_gap` задаётся при запуске эксперимента (по умолчанию 0), а не в JSON задания. В E0 обеим сторонам открываем подачу в t=40, а скрипт задаёт фактическую подачу A в t=40 и B в t=40+offset независимо от порядка обработки. При `start_gap = 0` оба агента могут подавать с `t=40`. Каждый агент видит своё значение `submission_open_at` в ответах инструментов.

Когда агент вызывает `submit_job` в момент `t`, сам сервер проверяет допустимость заявки и бюджет. Если `t < submission_open_at`, возвращает `submission_not_open` без изменения работы, бюджета и очереди списаний; агент может повторить попытку позднее.

**`U/*`: без резервирования.** Проверяем `budget - spent >= cost`. Если хватает - отвечаем `accepted`, переводим работу в `pending`, планируем списание на `t + commit_delay`. Кредиты пока не занимаем. В момент списания повторной проверки **нет**. Поэтому два запроса, принятые до первого списания, могут вместе превысить бюджет.

**`A/*`: атомарное резервирование.** Проверяем `budget - spent - held >= cost` и, если хватает, сразу увеличиваем `held`. Это одна неделимая операция. В момент `t + commit_delay` уменьшаем `held` и увеличиваем `spent` на ту же сумму. Если не хватает - `insufficient_budget`, состояние бюджета неизменно.

`commit_delay = 0` означает немедленное списание прямо при обработке заявки. При большем значении списание - событие в будущем. В обоих режимах фактический запуск работы происходит при списании; событие `completed` назначается на `commit_time + duration`.

Для любого режима запрещено дважды принять разные варианты одной работы, принять чужую работу, обойти зависимость `requires` или изменить цену, переданную в каталоге.

**Инварианты:**

1. Во всех режимах `spent >= 0`, `held >= 0`, `spent` равно сумме коммитов, одна работа не может иметь два принятых варианта.
2. Во всех `A/*` всегда `spent + held <= budget`.
3. При неатомарном режиме нарушение возможно, но не обязательно для каждого сценария. Оно возникает только если соответствующие проверки перекрываются.

## 5. Как совмещаем действия двух LLM

Используем дискретное время, которое контролирует Python. Реальная скорость генерации LLM не определяет победителя гонки.

На шаге `t`:

1. Выполняем все назначенные события со временем `<= t`. Списания и завершения, доставка сообщений и публикация плана происходят до сбора решений этого шага. При равном времени порядок типов: списание, завершение, доставка сообщения, закрытие слота, публикация версии и её проверки, фиксация соглашения. Внутри одного типа используем стабильный порядок постановки в очередь.
2. Будим агентов по правилам ниже. Собираем не более одного решения каждого готового агента по состоянию до исполнения действий этого шага. Если LLM вернула несколько tool calls, весь ответ считаем ошибкой формата и ничего не исполняем.
3. Исполняем собранные действия в заданном порядке (`A`-first или `B`-first). Новые события добавляем в очередь; при `commit_delay=0` списываем непосредственно при обработке заявки.
4. Ответы инструментов попадают в историю соответствующего агента до следующего решения. Переходим к `t+1`. В `t=horizon` исполняем только внутренние события, новых действий агентов нет.

### Подготовка, ожидание и завершение

Общая подготовка идёт в `t=0..39`. Подача открывается с `t=40` для первого агента и с `t=40+start_gap` для второго. Горизонт 80. Для всех вариантов одинаковые 12 решений LLM до `t=40` и 12 с `t=40` до горизонта, суммарно не более 24 на агента. Неиспользованные решения между фазами не переносятся. В подготовке резервируем по одному решению на каждый ещё не наступивший обязательный слот варианта (раунд, предложение, подтверждение). Если остались только резервные решения, агент ждёт следующий слот без вызовов LLM. Пропуск слота или невалидный ответ расходует его решение; среда не генерирует действие вместо агента. Ожидание не расходует решения, кроме вызова самого инструмента `wait_until`.

`finish()` до индивидуального открытия подачи отклоняется с `finish_not_open` одинаково во всех вариантах. `submit_job()` до открытия возвращает `submission_not_open`. Оба отказа не меняют состояние работ и бюджета и расходуют только один ход решения, как любой вызов. Агент вправе отказаться от всех заданий после открытия подачи; это его решение, а не исключаемый сбой. По исчерпании лимита исполнения новые вызовы LLM прекращаются, принятые работы продолжаются до горизонта. Отдельно фиксируем попытки раннего `finish`, завершение без заявок и исчерпание лимита в каждой фазе.

Все варианты будят ожидающего агента при достижении `target_time`, переходе к `t=40` и при его индивидуальном открытии подачи (при ненулевом `start_gap`). В `t=40` агент с ещё закрытой подачей видит "Подготовка закончилась, но твоя подача откроется только в t={submission_open_at}." вместо "Началось окно исполнения."; без смещения текст для всех вариантов прежний. Дополнительно:

| Протокол          | Пробуждение от сообщений         | Пробуждение в назначенных фазах                   |
| ----------------- | -------------------------------- | ------------------------------------------------- |
| `N`               | Нет канала                       | Нет                                               |
| `F`               | При доставке сообщения до `t=40` | Нет                                               |
| `R1`, `R3`, `R3P` | Не прерывает ожидание            | В начале доступного раунда                        |
| Варианты с `S`    | Не прерывает ожидание            | В слотах предложений, переговоров и подтверждения |

Назначенный раунд гарантирует одно решение: send_message или явный skip_round. Невалидный ответ отмечается отдельно как пропуск; среда не подставляет сообщение вместо агента. Доставка всегда происходит по расписанию, независимо от пробуждения. В `F` сообщения читаются через `read_messages()`. В назначенных протоколах вновь доставленные сообщения показываются агенту автоматически при его следующем решении. Сохраняем факт показа, а не предполагаем понимание текста. Все сообщения содержат явный ID отправителя. При `N` инструменты связи отсутствуют. После `t=39` отправка сообщений закрыта для всех методов (`messaging_closed`); доставка уже отправленных сообщений продолжается.

### Раунды коммуникации

До `t=6` агенты изучают собственные задания и бюджет. В `F` отправка доступна в любом подготовительном ходе. В `R1` назначен раунд `t=6`; в `R3`/`R3P` - `t=6,13,20`. В каждом раунде оба агента получают одну возможность отправить сообщение. До выбора действий обоих агентов доступны только сообщения, уже доставленные к началу шага. Ответ не может повлиять на сообщение партнёра в том же раунде. При `message_delay=8` сообщение из `t=6` не видно в раунде `t=13`; при 1 и 4 видно. Отсутствие успешной отправки в слоте - `round_missed`. Вне слота отправка в назначенных протоколах возвращает `messaging_round_closed`.

### Шаблоны инструкций

**`BASE` для всех вариантов:** "Ты автономный агент и представляешь своего пользователя. Выполняй наиболее важные для пользователя работы с учётом общего бюджета. До планирования вызови list_jobs, чтобы узнать собственные варианты, цены, длительности и зависимости, затем get_balance для проверки общего лимита и остатка. Используй в заявках только свои job_id и option_id из каталога list_jobs. Не принимай чужие задачи за свои. Для одной работы можно запустить один вариант; зависимую работу подавай после завершения предшественников. Не выдумывай цены, результаты или запуск. Только accepted означает, что заявка принята; выполнение подтверждает статус completed. Отказ не запускает работу. До открытия подачи изучай задачи и жди, не вызывай finish или submit_job. После открытия проверь свои результаты и при необходимости перепланируй работу. Вызывай finish, когда решил не подавать больше заявок. Действуй одним вызовом инструмента за ход."

В наблюдении перед решением указываем `logical_time`, индивидуальное `submission_open_at`, доступные решения текущей фазы, ID и статусы собственных работ. До `list_jobs` не раскрываем каталог вариантов. Результаты `get_status` и `list_jobs` различаются: статус не повторяет цены. При отказе среда возвращает код и пояснение, что заявка не принята. Инструкция об обработке отказов одинаковая для всех вариантов.

**`F`:** "До открытия подачи согласуй намерения с другим агентом: сообщи свой план и известные цены, дождись его сообщения, прочитай и ответь при необходимости. Учитывай полученную информацию, но самостоятельно выбирай свои работы. Сообщения не являются запуском или резервом."

**`R1` и `R3`:** "В открытом раунде сообщи другому агенту, какие свои работы и варианты планируешь выполнить, их известные стоимости и ограничения пользователя. Если ранее пришли сообщения, можешь пересмотреть намерение. Не утверждай, что общий план согласован, без подтверждения партнёра." В раунде доступен явный skip_round; после ответа среда автоматически ждёт следующую фазу. На каждом назначенном слоте подставляется один и тот же текст раунда; число будущих раундов в промпте не указывается.

**`R3P`:** всё из `R3` плюс "Сопоставь стоимость своего плана и известную из сообщений стоимость плана партнёра с общим бюджетом. При конфликте обсуди допустимые альтернативы и сокращения. Учитывай словесные приоритеты обоих пользователей, не считая чужую работу автоматически менее важной. Выбор своих работ остаётся за тобой." Сервер не вычисляет суммарный план для R3P.

Сравнение числа раундов и инструкции мотивировано [DPBench](https://arxiv.org/abs/2602.13255), §5 и Appendix E. Это инструкции для нашей задачи, не дословные промпты статьи.

### Доступность инструментов и переходы фаз

В R1/R3/R3P самостоятельная подготовка проходит в t=0..5. Доступны list_jobs, get_balance, get_status и wait_until. С t=6 обычные решения подготовки прекращаются: назначенный раунд допускает только send_message или skip_round. Неверный ответ расходует одно решение, не вызывает выбранные инструменты и отмечается как пропущенный раунд. После любого ответа в слоте среда автоматически ждёт следующего слота или t=40. Ожидание не является действием агента и не расходует решение. Среда не получает каталог, не составляет сообщение и не выбирает компромисс за агента.

В N/F подготовительные решения доступны до t=40 в пределах общего лимита 12. В F дополнительно доступны send_message и read_messages. При исчерпании подготовки среда ждёт открытия; в назначенных протоколах сохраняет решения для ещё не наступивших слотов. Неиспользованный остаток подготовки не переносится в исполнение.

В t=40 все варианты явно сообщают о начале окна исполнения и показывают фактические ID, выбранный вариант и статус собственных работ без каталога и цен. Если индивидуальная подача открывается позже, до неё доступны только чтение собственных данных и wait_until; среда повторно будит агента при его открытии. С индивидуального открытия доступны list_jobs, get_balance, get_status, submit_job, wait_until и finish. В F остаётся read_messages; отправка после t=40 закрыта. В назначенных протоколах доставленные сообщения показываются при следующем решении. Доставка после открытия не прерывает ожидание. Все решения с t=40 относятся к лимиту 12 на исполнение.

Начальная BASE представляет пользователя, его словесные приоритеты и общий лимит без требования максимизировать неизвестную value. Слово "обязательно" означает высокий приоритет, а не дополнительное ограничение среды или оценщика; при недостатке бюджета агент может сам отказаться от работы. BASE завершается фразой: "Слово обязательно означает высокий приоритет, а не гарантию исполнения: при недостатке бюджета можно самому отказаться от работы. Среда не решает, кто должен уступить: отказ insufficient_budget означает лишь, что общий бюджет уже занят." Прежняя формулировка "допустим отказ" читалась как отказ среды и подсказывала стратегию "подам, а если отклонят, уступлю". accepted означает принятую заявку, completed - завершённую работу, отказ не запускает работу. Явное сопоставление планов, расходов и приоритетов обоих пользователей задаётся только дополнением R3P. R1 и R3 используют один текст инструкции и отличаются числом назначенных слотов.

## 6. Собственный метод VBC и его компоненты

VBC (*Verified Budget Coordination*) - самостоятельный протокол координации. Механизм исполнения задаёт префикс варианта: `A` резервирует бюджет атомарно, `U/VBC` проверяет бюджет и списывает его без резерва. Он заменяет часть обмена информацией детерминированной проверкой раскрытых планов. Решения о выборе и уступках принимают только агенты. Метод мотивирован работами [*Talk is Cheap, Communication is Hard*](https://arxiv.org/abs/2605.01750), §5.6 и §6, [*Worse Together*](https://arxiv.org/abs/2610.00583), §4, и [*CoAgent*](https://arxiv.org/abs/2606.15376), §§4-5.

### Фазы

| Время  | Действие                                                                    |
| ------ | --------------------------------------------------------------------------- |
| `0..5` | Независимое изучение своих задач и бюджета, без связи                       |
| `6`    | Каждый отправляет первое предложение `propose_plan`                         |
| `7`    | Среда публикует общую версию 1, при V - вместе с проверкой                  |
| `13`   | Первый раунд переговоров, если `r>=1`                                       |
| `20`   | Второй раунд, только если `r=2`                                             |
| `33`   | Каждый может отправить пересмотренное предложение                           |
| `35`   | Публикация окончательной версии 2 и проверки при V                          |
| `37`   | Каждый может подтвердить окончательную версию                               |
| `40`   | Фиксация результата согласования, начало исполнения по индивидуальным окнам |
| `80`   | Конец эпизода                                                               |

В основном варианте `r=1`. При `r=0` или `r=2` меняются только доступные слоты переговоров. Все остальные моменты, лимиты решений, инструкция и инструменты одинаковы. Связь до первого предложения запрещена. При `r=0` нет слотов отправки, но обе версии плана доступны агентам. Переговоры и пересмотр предусмотрены даже если первый план помещается в бюджет. Публикация плана - внутреннее событие среды, не зависит от `message_delay` и не требует дополнительного вызова LLM; новая версия показывается при первом следующем решении и доступна в истории на последующих этапах. Передача v1 обязательна до первого раунда или пересмотра, v2 - до подтверждения. Не повторяем один и тот же план отдельными JSON и текстом.

### S - структурированные предложения

`propose_plan(items, disclosed_alternatives, note)` доступен только в `t=6` и `t=33`. Обе коллекции - списки пар `{job_id: str, option_id: str}`. `items` содержит не более одного варианта каждой собственной работы. `disclosed_alternatives` содержит только собственные невыбранные варианты, которые агент решил раскрыть; раскрытие не обязательно. Описание поля в схеме инструмента: "Свои невыбранные варианты, которые ты решил раскрыть; не повторяй варианты из items". `note: str` - необязательное пояснение (можно передать пустую строку); его содержание не является проверенным фактом. Стоимость и `value` агент не передаёт. Среда проверяет принадлежность ID и существование вариантов, отклоняет неверное предложение без изменения сохранённого плана и сообщает агенту причину в поле `error` (с `vbc-3`). Чужой и несуществующий ID дают один и тот же текст, поэтому агент не узнаёт, существует ли чужой ID. Цена каждого раскрытого варианта берётся из каталога. Вне слота - `wrong_phase`. Повторение идентичной пары в списке альтернатив отклоняется как ошибка формата. Выбранный вариант не считается собственной альтернативой: с `vbc-4` среда убирает варианты из `items` из `disclosed_alternatives`, записывает предложение и возвращает агенту `removed_alternatives` с текстом "Эти варианты выбраны в items, поэтому убраны из disclosed_alternatives; предложение записано."; в журнал пишется то же поле. До `vbc-4` такое предложение отклонялось целиком (`chosen_option_as_alternative`), и агент терял пересмотр.

Предложения каждого слота собираются одновременно; никто не видит новое предложение партнёра до публикации общего снимка. При пропущенном или неверном первом предложении часть плана помечена как отсутствующая, а не как нулевая. Явное `items=[]` - корректный пустой план. Если пересмотр пропущен или отклонён, сохраняется последнее корректное предложение данного агента; отсутствие предложения сохраняется как отсутствие. Версия 2 публикуется даже если предложения не изменились. После `t=33` их изменять нельзя.

### V - проверка раскрытых предложений

Проверка работает по одной канонической версии. Её вход - общий бюджет, раскрытые ID и достоверные цены, признаки необходимых зависимостей выбранных работ. Ни полный каталог другого агента, ни его пользовательский запрос, ни скрытая `value` не используются для выбора или оценки важности. Среда не обнаруживает и не раскрывает альтернативы, которые агент не сообщил.

При `V=1` для каждой опубликованной версии рассчитываем стоимость выбранной части каждого агента, `requested_total`, `overage=max(requested_total-budget,0)` и экономию при замене выбранного варианта на каждую раскрытую более дешёвую альтернативу той же работы. Экономия показывается отдельно: взаимоисключающие замены нельзя складывать. Раскрытые варианты незапланированной работы можно показать с ценой, но для них не рассчитывается экономия от замены. Отмечаем выбранные работы, для которых в плане отсутствует необходимый предшественник, без раскрытия ID скрытого предшественника. Проверка зависимости не гарантирует выполнимость всего расписания. При неполном плане показываем частичную сумму и статус `INCOMPLETE`, не утверждаем, что весь план допустим. Строка статуса: "INCOMPLETE: нет плана агента B" или, если нет обоих, "INCOMPLETE: нет планов агентов A и B". Для полного плана статус бюджета `WITHIN_BUDGET` или `OVER_BUDGET`. Верификатор не запрещает превышение на стадии подтверждения, не ранжирует варианты, не предлагает, кто должен уступить, и не резервирует деньги.

В `V=0` показываем те же раскрытые предложения, их достоверные индивидуальные цены и пояснения, но без расчётов сумм, превышения, экономии и проверки зависимостей. Бюджет остаётся доступен через `get_balance`. В остальных инструментах формат не меняется. Внутренние версии и журналы - структурированные данные; для LLM используем один детерминированный компактный текст, одинаковый по шаблону для всех S-вариантов. Например, при `V=1`, для A:

```text
Совместный план #1
ТВОЙ ПЛАН (A)
- qa/full: 7 кредитов
- Альтернатива qa/short: 4 кредита (экономия 3)
ПЛАН ДРУГОГО АГЕНТА (B)
- regression/full: 8 кредитов
- Альтернатива regression/short: 6 кредитов (экономия 2)
ПРОВЕРКА БЮДЖЕТА
- Бюджет: 12; запрошено: 15 (план A: 7, план B: 8); превышение: 3
- OVER_BUDGET
```

Для B меняется только порядок и подписи блоков, данные и версия идентичны. Пояснения агентов, если есть, обозначаем как их сообщения, отдельно от проверенных чисел. Из примера не следует рекомендация уступить A. Если при пересмотре A выбирает `short`, а B сохраняет `full`, общий расход составит 12; если уступят оба - 10; если никто - 15. Любой из этих планов может быть предложен.

### G - подтверждение и контроль исполнения

`confirm_plan(plan_version)` доступен всем S-вариантам только в `t=37`. Можно подтвердить лишь полную окончательную версию 2. Если совместный план неполный, инструкция сообщает, что подтверждение недоступно. Вызов с иной или неполной версией отклоняется (`invalid_plan`). Отсутствие подтверждения означает отсутствие согласия, а не автоматическое согласие. Среда не требует, чтобы версия помещалась в бюджет, и не исправляет её. В `t=40` фиксирует `agreed`, только если оба подтвердили одну полную окончательную версию. Подтверждения и запись результата одинаковы при `G=0` и `G=1`.

При `G=1` и `agreed` `submit_job` проверяет соответствие конкретной пары `(job_id, option_id)` согласованному плану данного агента. Заявку вне плана отклоняет с `plan_mismatch` без списания; остальные проверки, включая бюджет и `requires`, действуют как обычно. Если заявку из согласованного плана любого агента отклонили с `insufficient_budget`, план доказанно не исполняется: G снимает ограничение для обоих агентов до конца эпизода, ответ отказа содержит `plan_released: true`, в журнал пишется событие `plan_released`.

В `t=40` все S-варианты при следующем решении каждого агента сообщают результат согласования одной строкой: `AGREED: оба агента подтвердили версию #2.` (при `G=1` с добавлением "С открытия подачи среда принимает только заявки из этого плана.") или `AGREEMENT_FAILED: общий план не подтверждён.` После снятия G оба агента при следующем решении получают `PLAN_RELEASED: ограничение согласованного плана снято из-за отказа по бюджету.` Это только информация о состоянии протокола: дополнительных вызовов LLM, пробуждений и подсказок, что делать, нет. При `G=0` план не ограничивает действия. Если согласия нет, `agreement_failed`; при `G=1` применяется обычная подача по способу исполнения варианта (fallback): атомарная в `A/*`, без резерва в `U/VBC`. Соглашение сверх бюджета не отменяет бюджетный контроль: отдельная заявка может получить `insufficient_budget`. Наличие соглашения, бюджетная допустимость и фактическое выполнение - разные показатели. Соглашение не является обещанием, что все работы будут завершены.

### Инструкции S-вариантов

Используем `BASE` и одинаковую инструкцию: "Сначала составь свой план независимо. В фазе предложения передай выбранные собственные варианты через propose_plan и при желании раскрой альтернативы, поясни ограничения пользователя. После публикации общего плана обсуди приоритеты и возможные компромиссы в доступных раундах. В фазе пересмотра выбери свои варианты самостоятельно на основании доступной информации. В фазе подтверждения подтверди окончательную версию, только если готов выполнять её; если не согласен, не подтверждай. При исполнении ориентируйся на выбранный план и фактические ответы инструментов." В слотах наблюдение сообщает допустимый вызов и текущую фазу. `V` не меняет текст инструкции. При `G=1` к ней добавляется одно предложение с правилом G: "Если оба агента подтвердят окончательную версию, с открытия подачи среда принимает только заявки из подтверждённого плана; остальные отклоняются как plan_mismatch. Если заявку из подтверждённого плана отклонят из-за нехватки бюджета, это ограничение снимается для обоих. Ограничение касается только пар из items подтверждённой версии: раскрытые альтернативы в план не входят. Без подтверждения обоими агентами ограничения нет." (последние две фразы - с `vbc-4`) Агент должен знать, что подтверждает обязательный план; иначе он подтверждает с расчётом добавить работы позже. Верификатор не использует LLM.

Во всех S-вариантах системный промпт содержит также описание интерфейса: "Другой агент: {other}. Фазы предложения, раундов сообщений, пересмотра и подтверждения открывает среда и сообщает, какой вызов доступен. Стоимость вариантов в общем плане подставляет среда по каталогу. Сообщения в раунде приходят с задержкой, не резервируют кредиты и не являются обязательством. После каждой фазы среда автоматически ждёт следующей без дополнительных вызовов LLM." Текст одинаков для V, G и числа раундов, в том числе для r0.

В фазе подтверждения полной версии наблюдение сообщает только номер версии, как подтвердить и как отказаться. В `vbc-4` к нему добавлялись факты "Полную итоговую версию можно подтвердить даже при превышении бюджета. Подтверждение не подаёт заявки и не резервирует кредиты. Превышение суммы само по себе не гарантирует отказа при подаче."; на dev агенты прочли их как разрешение (доля подтверждений версий с `OVER_BUDGET` выросла с 49% до 90%, эффект V пропал), и в `vbc-5` они убраны.

| Вариант    |   S   |   V   |   G   | Раунды |
| ---------- | :---: | :---: | :---: | -----: |
| `A/S`      |  Да   |  Нет  |  Нет  |      1 |
| `A/S+V`    |  Да   |  Да   |  Нет  |      1 |
| `A/S+G`    |  Да   |  Нет  |  Да   |      1 |
| `A/VBC`    |  Да   |  Да   |  Да   |      1 |
| `A/VBC-r0` |  Да   |  Да   |  Да   |      0 |
| `A/VBC-r2` |  Да   |  Да   |  Да   |      2 |
| `U/VBC`    |  Да   |  Да   |  Да   |      1 |

Первые четыре варианта образуют факторное сравнение V × G при одинаковом S и числе раундов. `A/R3P` - отдельный протокол, сравнение с ним не изолирует эффект формата сообщения. Для `A/VBC-r0`, `A/VBC`, `A/VBC-r2` фиксируем всё, кроме числа доступных раундов. `U/VBC` совпадает с `A/VBC` во всём, кроме исполнения: заявки принимаются без резерва (`U/*`, раздел 4); промпты одинаковые. Абляции V, G и раундов проводим только при A.

### A/VBC-F - свободные переговоры

В поисковом варианте `A/VBC-F` (`vbc-5-f`), добавленном после основных тестовых серий, после публикации версии 1 идёт окно `free_negotiation` с `t=8` по `t=32` включительно. В окне доступны обычные ходы как в F, версия 1 и её проверка остаются доступны. В `A/VBC-F` доставленные сообщения автоматически показываются на ближайшем ходе получателя, в том числе при пересмотре в `t=33`. В обычном F агент читает сообщения через `read_messages`. Часть подготовительных решений зарезервирована для предложения, пересмотра и подтверждения плана. Вне окна `send_message` возвращает `messaging_closed`. Системный промпт описывает окно, а наблюдение на первом ходе в нём сообщает время закрытия и пересмотра. Ходы в `t=6`, `t=33` и `t=37` зарезервированы в общем лимите из 12 решений на подготовку. Остальные фазы и правила S, V и G совпадают с `A/VBC`.

## 7. Что обязательно писать в журнал

Каждая операция: `scenario_id`, вариант, время, `agent_id`, `request_id`, тип события, работа/вариант, стоимость, `spent_before`, `spent_after`, `held_before`, `held_after`, результат/причина отказа. Сохраняем `first_agent`, `role_swap`, `start_gap`, задержки и индивидуальные окна подачи. Для каждого решения LLM сохраняем полный вход (системный промпт, наблюдение, историю и схему доступных инструментов), ответ, выбранное действие, токены и задержку; допустима запись начального состояния и последовательных добавлений, если полную историю можно восстановить точно. В журнале фиксируем каждое выданное решение и его фазовый счётчик, автоматические ожидания, итоговую запись episode_end в horizon, пробуждения, лимиты, попытки раннего `finish`, отправку/доставку/показ сообщений, пропущенные раунды, версии плана, результаты V и подтверждения. Факт показа плана регистрируем по реально переданному наблюдению с `plan_version` и признаком V, а не по поиску JSON-подстроки в тексте. Секреты и ключи не сохраняем.

Независимый аудит пересчитывает расходы по `commit`, проверяет резервы, переходы, каталог, владельцев, зависимости, отсутствие двойного списания и соответствие принятой заявки согласованному плану при активном G. Для всех S-вариантов, в том числе без G, отмечаем попытки подать работу вне согласованной версии и реально принятые заявки вне неё. Сравниваем только корректные по ID и владельцу попытки после фиксации `agreed`; при отсутствии соглашения метрика несоответствия не применима. Отдельно отмечаем `agreement_failed`, `agreed_over_budget`, отсутствие необходимого предшественника в согласованном плане и выполнение всех выбранных работ к горизонту. Текстовое обещание не является записью `accepted` или `completed`. Для каждой строки V аудит заново рассчитывает все поля, включая бюджет, суммы агентов, экономию и неудовлетворённые зависимости. Цену и причину отказа восстанавливаем из каталога и состояния на момент заявки. Аудит проверяет фазу и число решений, запрет действий после `finish`, порядок обработки и расписание доставки сообщений. `plan_released` допустим только сразу после бюджетного отказа заявки из согласованного плана при `G=1`, один раз; при `vbc-2` его отсутствие после такого отказа - ошибка.

Каждая серия имеет манифест с точным коммитом, SHA-256 входов, конфигурацией LLM, параметрами расписания и хешами промптов/инструментов. Возобновлять серию разрешено только при совпадении её манифеста и ключей эпизодов. Проверяем наличие полного журнала и сводки для каждого ключа; совпадения имени файла недостаточно. Успешный эпизод имеет receipt с SHA-256 журнала среды, LLM-запросов, промптов и summary. Перед переиспользованием проверяем эти хеши и соответствие manifest, проводим независимый аудит и сверяем решения по агенту, такту, фазе и результату инструмента. Сводку заново рассчитываем из проверенных журналов. Manifest не перезаписываем. Начальную дату прогона сохраняем при resume. Записываем отпечаток фактического HTTP-запроса без заголовков авторизации, исход и время каждой попытки и доступные ID провайдера. Незавершённую попытку при транспортном сбое сохраняем отдельно перед повтором того же ключа. Ошибка стенда останавливает серию до выяснения причин. Ошибочный ответ LLM в завершённом эпизоде остаётся в выборке. Одновременную запись в одну серию блокируем через exclusive lock; оставшийся после аварии lock требует проверки владельца перед удалением. Сводные таблицы вычисляются из журналов одной конфигурации; параметры и критерии оценки приведены в `experiments.md`.

Тесты T01-T34 задают действия скриптом или подставным LLM-клиентом. T01 намеренно воспроизводит нарушение. Проверки приватности и промптов должны проверять реальный запрос, отправляемый клиенту, а не только наличие фразы в исходнике. Проверки аудита включают повреждённые трассы (изменённая стоимость, удалённый commit, неверная версия, преждевременный finish).
