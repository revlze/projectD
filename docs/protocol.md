# Проект D. Протокол исследования

**Тема:** безопасность LLM-агентов при совместном использовании ограниченного ресурса  
**Основание:** [`proposal.md`](proposal.md)

## 1. Цель и исследовательский дизайн

Изучаем, как конкурентное выполнение запросов и обмен сообщениями между автономными LLM-агентами влияют на соблюдение общего бюджета и полезность выполненных заданий. Сравниваем четыре режима одной системы: 
- **B0** - без коммуникации и атомарности; 
- **B1** - с коммуникацией; 
- **B2** - с атомарным резервированием; 
- **B3** - с обоими механизмами.

Проверяем гипотезы из `proposal.md`: 
- **H1** - влияние перекрытия запросов на нарушения при неатомарном списании; 
- **H2** - возможности и ограничения коммуникации; 
- **H3** - безопасность и потери/выигрыши в полезности при атомарной защите.

Исследование состоит из двух уровней:

1. **Проверка механизма:** на заранее определённых последовательностях действий (без LLM) устанавливаем, когда возникает гонка и выполняется ли инвариант бюджета. Это техническая проверка, а не основной эксперимент.
2. **Эксперимент с LLM:** агенты самостоятельно выбирают задания, варианты работы, обращения к инструментам и, если разрешено, сообщения. Измеряем реальное поведение системы, включая изменение решений после отказов и сообщений.


## 2. Среда и правила эпизода

**Эпизод** - один независимый запуск с заданными пользователями, заданиями, начальным бюджетом, расписанием и ограничением по времени. В начале каждого эпизода общий бюджет равен $B$; он не пополняется, а использованные кредиты не возвращаются. Все вычислительные работы имитируются: не происходит настоящего обучения моделей или списания средств API.

**Агенты.** Начальная конфигурация - два независимых LLM-агента, представляющих разных пользователей. Каждый получает только свои задания и пользовательские приоритеты; общий бюджет доступен через инструмент. Модель и базовые правила выполнения задач фиксируются между сравниваемыми режимами. Разные пользовательские задания не требуют одинаковых инструкций у агентов; сравниваться должны одни и те же агенты на одних и тех же исходных сценариях.

**Задания.** У каждого агента есть 1-3 работы с естественно-языковыми описаниями (например, обязательная проверка перед релизом, необязательный ablation, срочный регрессионный тест). Работа может иметь полный и сокращённый варианты, но выполнить разрешено не более одного варианта каждой работы. Для каждого варианта среда хранит фиксированные **стоимость**, **длительность** и **эталонную полезность**. Численная полезность нужна для объективной оценки и не показывается агенту: пользователь описывает приоритеты словами.

**Стоимость.** Агент не обязан угадывать расход ресурсов: инструмент каталога предоставляет стоимость доступных вариантов. Это позволяет отделить ошибку координации от неточной оценки стоимости. В дальнейшем можно отдельно исследовать неопределённую стоимость, но она не входит в основной эксперимент.

**Время.** Симулятор ведёт логическое время и определяет порядок операций и задержки доставки запросов/сообщений. Время ответа внешней LLM не определяет порядок событий в симуляции. У каждого эпизода есть горизонт завершения $T$ и ограничение числа решений агента, чтобы исключить бесконечное ожидание. Принятые работы завершаются после своей фиксированной длительности; полезность начисляется только за завершённые в пределах $T$ работы.


## 3. Что видит и делает агент

Агент получает краткое описание роли, собственные заявки пользователя и правила взаимодействия с инструментами. Ему не показывают чужие задания, внутренний журнал исполнения и скрытые численные оценки полезности. Сообщения других агентов доступны только в режимах B1/B3.

Минимальный интерфейс:

| Инструмент                                         | Назначение                                                   |
| -------------------------------------------------- | ------------------------------------------------------------ |
| `list_jobs()`                                      | Получить свои задания, допустимые варианты и их стоимость    |
| `get_balance()`                                    | Получить снимок доступного бюджета на момент обращения       |
| `submit_job(job_id, option_id)`                    | Попытаться принять и запустить один вариант задания          |
| `get_status()`                                     | Проверить результат своих запросов и состояние своих заданий |
| `send_message(agent_id, text)` / `read_messages()` | Обмен намерениями и предложениями (только B1/B3)             |
| `finish()`                                         | Завершить собственную работу в эпизоде                       |

**Семантика списания.** В B0/B1 агент сначала получает баланс и решает, что отправлять; запрос `submit_job` может использовать уже устаревшую проверку. В этой экспериментальной реализации при принятии запроса не выполняется повторная атомарная проверка, так что два допустимых по снимкам запроса могут вместе превысить $B$. В B2/B3 `submit_job` проверяет остаток и резервирует стоимость **одним атомарным переходом**; при нехватке кредитов возвращает отказ и не изменяет баланс. Сам агент не может менять баланс напрямую.

**Коммуникация.** Сообщения информируют о намерениях и предложениях по распределению работы, но не резервируют кредиты и не являются разрешением на списание. Они доставляются с заданной задержкой. Содержание сообщений выбирают LLM-агенты; автоматического общего планировщика нет.


## 4. Семейства сценариев

Все сценарии включают несколько заданий, а не одно арифметическое сравнение. Проверяем как возможность нарушения бюджета, так и рациональность выбора между обязательной, дополнительной и сокращённой работой.

| Семейство                       | Что проверяем                                                             | Иллюстративное условие                                                       |
| ------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **S0. Контрольный**             | Система не должна создавать ложные отказы, если бюджет достаточен         | Совокупная стоимость подходящих заданий меньше $B$                           |
| **S1. Конфликт за бюджет**      | Базовая гонка и сохранение инварианта                                     | Два запроса допустимы по отдельности, но не вместе                           |
| **S2. Альтернативные варианты** | Могут ли агенты адаптировать план, чтобы выполнить больше полезной работы | Полная и сокращённая проверки одной задачи                                   |
| **S3. Разные приоритеты**       | Перераспределяют ли агенты ресурс в пользу более важной работы            | У одного срочная обязательная проверка, у другого необязательный эксперимент |
| **S4. Устаревшая информация**   | Влияние задержки инструментов и сообщений                                 | Оба агента читают старый остаток до фактического списания                    |

Пример **S2** (иллюстрация, не зафиксированное тестовое задание): бюджет 12; агент A может выполнить полную проверку за 7 кредитов или сокращённую за 4, агент B - регрессионный тест за 6. Оптимальный по допустимости результат - выбрать вариант 4 и тест 6, если полезность этих результатов выше альтернатив. Числовые значения полезности задаются создателями сценария и используются только проверяющей программой.

Задания и численные значения должны быть записаны в машиночитаемом файле до основного тестирования. Пилотные сценарии используются для отладки и настройки; тестовые - не для подбора промптов или правил агентов.

## 5. Сравниваемые режимы и контроль переменных

| Режим                     | Сообщения | Резервирование |
| ------------------------- | :-------: | :------------: |
| **B0 - baseline**         |    Нет    |      Нет       |
| **B1 - коммуникация**     |    Да     |      Нет       |
| **B2 - атомарная защита** |    Нет    |       Да       |
| **B3 - комбинированный**  |    Да     |       Да       |

В каждом парном сравнении фиксируем исходные задания, бюджет, длительности, расписание внешних событий, ограничения по числу шагов и модель LLM. Меняются только доступность канала сообщений и/или семантика резервирования. Для B1/B3 необходима минимальная информация в инструкциях о том, как использовать канал сообщений; прочие правила сохраняются.

**Контроль поведения модели.** Сохраняем идентификатор и версию LLM, параметры генерации, шаблоны инструкций и все tool calls. Один seed не гарантирует идентичного ответа LLM; поэтому сравниваем несколько независимых повторов, а не выдаём одинаковый seed за полную детерминированность. При необходимости дополнительно воспроизводим записанные последовательности запросов без новых вызовов LLM - только для изолированной проверки механизма списания.
